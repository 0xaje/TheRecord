        Which version did both people approve?
        

        An agreement can change in a single word. The Record connects each file version to its approvals on QoreChain Diana Testnet.

        A small edit can change the agreement.
        

        Anyone who needs to approve a document version can use this workflow. Our example follows a client and a freelancer who agree to delivery by Friday. Later, someone shares a copy that says Monday. The question is simple. Which file did both people approve?
        

        The Record lets two parties review terms, approve a specific version, and check a copy against that record later. A file fingerprint ties the approvals to the exact bytes of the document.
        

        The example in the walkthrough uses the real Friday and Monday sample files available in the demo. The chapter illustrations explain the workflow. Screenshot results and receipt links identify the recorded evidence.
        

        The question appears in real disputes.
        

        The Record addresses a specific uncertainty: which file version did the designated signing accounts approve? These examples explain why clear agreement records matter. They are not claims that this app would have prevented a lawsuit or guaranteed payment.
        

        United Kingdom: which terms applied?
        In RTS Flexible Systems v Müller, work began before the intended formal contract was signed. The dispute reached the UK Supreme Court over whether a contract existed and which terms governed it.
        Read the official case summary
        

        Canada: did a reply mean approval?
        In Achter v South West Terminal, a photographed contract received a thumbs-up reply. The meaning of that response became disputed. The result depended on the parties’ circumstances and earlier dealings.
        Read the Canadian court’s case record
        

        Nigeria: keeping contract records inspectable
        Nigeria’s Open Contracting Portal already publishes procurement information. OGP’s April 2026 review records improvements alongside remaining data-entry and paperwork work. This is local context for the importance of accessible records, not a claim that public procurement and everyday agreements have identical needs.
        Read the Nigeria assessment
        

        Our conclusion is narrower than these disputes: explicit approvals tied to an exact file can provide a clearer reference. A wallet signature does not by itself establish legal identity, authority, informed consent, delivery or payment.
        

        Read the research, comparison with existing signing tools and its limits
        

        From review to proof
        

        1. Review the terms. Create a private draft, keep your workspace recovery code, save a revision and share an invitation with its access code. The reviewer can request changes before signing.
          2. 

        2. Record the file. Download the agreed revision. Use Record to submit its fingerprint and two distinct signer addresses to Diana.
          3. 

        3. Approve through QoreX. Each signer opens the verification link in QoreX, selects Diana Testnet and verifies the exact file before approving. Both approvals must refer to the same version.
          4. 

        4. Verify later. Anyone with the file and agreement ID can compare its fingerprint with the recorded version. Checking a finalized file requires no wallet connection.
          5. 

        5. Amend with fresh consent. The original proposer records a changed file as a new version after the current one finalizes. Both people approve again. Earlier versions remain verifiable.
        

        Where QoreChain makes the difference
        

        The Record is being built for QoreChain’s Build Before Q-Day event in the Post-Quantum dApp track. Its working agreement contract is deployed on QoreChain Diana Testnet.

        The approval message binds the signature to the chain, contract, agreement, version, file fingerprint and signer. That connection is the reason the signature belongs to a particular approval.

        Keep draft history separate from chain history.
        

        Saved private revisions
        Each new save retains a revision. In Drafts, open Saved revisions to view or download an earlier draft without replacing the editor. These revisions stay in your workspace; saving one does not create a Diana agreement version.
        QoreChain agreement history
        History reads version, approval and finalization events from Diana and compares them with a contract-state snapshot. Continue an incomplete scan before treating it as the full history. Anyone can inspect the public records without connecting a wallet.

        Privacy, recovery and deletion
        

        File verification hashes your selected file in your browser. The verification operation sends a chain lookup and compares the result locally. The document itself stays on your device during this check.
        

        The private draft workspace saves the draft on the service so invited reviewers can read it. Draft access uses invitation links and codes. Workspace access uses a private recovery code; anyone holding it can access the workspace. These drafts are not end-to-end encrypted. Server storage is a different operation from local file verification.
        

        The agreement contract stores fingerprints, signer addresses and approval state. A fingerprint helps detect changes. Approval records identify the signing accounts. Keep your own copy of each agreed document.
        Save your workspace recovery code outside the browser. Clearing browser data can remove its saved copy. If storage is blocked, file checking can still work, while workspace actions stop if a recovery identity cannot be safely saved.
        Trash keeps revisions and revokes old review links. Restore a draft and create a new invitation to share it again. Permanent deletion requires typing DELETE and removes that draft, revisions, invitations and feedback from the live database. It cannot be restored. Downloaded copies and public QoreChain records remain; backup erasure is unverified.
        A public fingerprint is not encryption: someone who guesses the exact file can compare its hash. Keep the original file; the chain fingerprint cannot recreate it.
        

        What we have verified
        

        The Diana evidence log records two distinct approvals, finalization, changed-file rejection and fresh approvals for amendments. It also records the earlier version remaining verifiable after an amendment.
        

        The guided demo’s original and changed-file results were captured on a laptop. The owner repeated both checks inside QoreX on a phone and confirmed working downloads. QoreX blocked screenshots on that phone, so its results are recorded as owner reports.
        

        The owner completed the agreement flow using two distinct wallets. Independent participants completing the full workflow are still pending. The separate scoped-window admission test passed; that test created a record but did not approve or finalize it.

        Audit and regression evidence
        Both QCAIA reports match the contract source after final-newline normalization. The first scored 65/100 Medium and the latest re-audit scored 65/100 High. Findings remain Open in those reports; the repository records our finding-by-finding responses and remaining design tradeoffs.
        Six owner-run Solidity tests passed, plus four read-only historical Diana checks covering a valid approval and rejection of duplicate, wrong-version and altered signatures. Local JavaScript checks cover the workspace and verification controls. These are test results, not an independent security certification.
        Audit reports and raw regression logs · Scoped-window receipts and rejection evidence
        

        Build, service limits and technical checks
        The repository includes a pinned Node version, local Worker/SQLite setup and automated checks. Hosted private drafts use a Worker and D1. The service limits workspaces to 50 drafts, 200 revisions per draft and 100 invitations per draft, with paginated lists and request throttling. Limits are operational controls, not protection against every abuse scenario.
        Legacy sign-in relies on a trusted hosting identity header. Moving the backend to a different host requires preserving that trust boundary. Backup erasure and independent full-workflow acceptance remain unverified.
